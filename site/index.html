Editor desktop para artigos em Typst · em desenvolvimento

Revise artigos em Typst com seus coautores, sem servidor no meio.

O Prelo é um editor desktop, em construção, para quem escreve artigos científicos a várias mãos. Coautores vão poder sugerir, comentar e aceitar mudanças no mesmo arquivo .typ, com a prévia do PDF ao lado. O texto vai de um computador ao outro sem passar por um servidor que o guarde.

Estado do projeto: em desenvolvimento. Ainda não dá para escrever artigos com ele.

Existe hoje o esqueleto do app (uma janela que mostra versão e sistema, a suíte de testes e a auditoria de dependências) e o pipeline que gera os instaladores. O editor local está em andamento. Compilador, colaboração e revisão são planejados. Tudo o que esta página descreve no futuro ainda não existe.

Ver o código no GitHub Baixar a v0.1.0 (abre a página da versão no GitHub)

A v0.1.0 é só o esqueleto: a janela abre e mostra a versão, mas o editor ainda não existe. Há instaladores para macOS, Windows e Linux (RNF-01). O app não é assinado, então macOS e Windows mostram um aviso ao abrir. As notas da versão explicam como abrir e como conferir o checksum.

O problema: a revisão a várias mãos

O Typst compila em milissegundos e tem sintaxe mais limpa que a do LaTeX. Num artigo com coautores, orientadores e revisores, porém, o que mais consome tempo é a revisão: alguém sugere uma frase, outro comenta uma figura, o autor principal aceita parte e rejeita o resto. Hoje esse ciclo se espalha por ferramentas que não juntam tudo isso para Typst.

Controle de alterações só no LaTeX

O Overleaf tem controle de alterações e papel de revisor, mas só funciona com LaTeX.

Typst na web, só online

O Typst web app tem edição em tempo real e comentários (com dono no plano Pro), mas não documenta controle de alterações e não funciona offline.

Revisão virando diff do git

VS Code com Tinymist e git funciona offline e tem boa prévia. A revisão, porém, vira diff do git e comentário dentro do código-fonte.

Fonte: levantamento de novembro de 2026 feito a partir da documentação de cada ferramenta, em especificação §2. A tabela completa inclui TeXlyre, Collabst e TINO.

O que o Prelo vai fazer de diferente

Revisão por sugestão

Antes: a mudança de um revisor entra direto no texto ou chega por e-mail.

Depois: no modo Sugerindo, cada mudança vira uma sugestão marcada com a cor de quem a fez. Você aceita ou rejeita uma a uma ou em lote, e pode desfazer.

Uma sugestão que quebraria a compilação aparece com aviso, e o Aceitar fica desativado.

RF-10 a RF-15

Colaboração sem servidor

Os computadores dos coautores se conectam direto: na rede local ou pela internet. Nenhum servidor guarda o artigo, e o tráfego é criptografado de ponta a ponta. Não há conta nem senha: cada pessoa tem uma chave criada no próprio computador.

Quem não está online ao mesmo tempo recebe o trabalho pelo git do grupo.

RF-20 a RF-23, RNF-02

Compilador Typst embutido

Ninguém precisa instalar o typst. O Prelo compila sozinho, e prévia, diagnósticos e PDFs saem do mesmo compilador. A versão fica registrada no projeto, para todos os coautores compilarem igual.

Meta: prévia em menos de 100 ms após uma edição, em artigos de até 40 páginas. É meta, não medição.

RF-02, RF-06, RF-07

Local-first, com o .typ limpo no git

O artigo mora no seu computador e num repositório git. O .typ é sempre Typst puro, compilável fora do Prelo; sugestões e comentários ficam numa pasta separada, .prelo/.

Offline você comenta e sugere. Salvar (⌘S) recebe as mudanças dos outros, envia as suas e grava um commit.

RF-30 a RF-36, RNF-04, RNF-05

Primeiros passos: do zero ao PDF Tutorial

Neste tutorial você vai criar um artigo curto, ver a prévia mudar enquanto digita e exportar o PDF. Não precisa de coautores nem de internet.

  1. Instale e abra o Prelo. A versão publicada hoje (v0.1.0) ainda não tem o editor; este passo vale a partir da versão que trouxer a fase 1. Na primeira abertura, digite seu nome e escolha uma cor. O app cria sua chave; não há conta nem senha.
  2. Crie o projeto. Na tela inicial, escolha Novo projeto Typst. Dê o nome meu-artigo.
    Pasta padrão, conteúdo inicial do projeto e se o app já cria o repositório git: a definir.
  3. Escreva o título e a primeira seção. No arquivo main.typ, digite: 
    #set document(title: "Meu primeiro artigo")
#set text(lang: "pt")

= Introdução
Este é o primeiro parágrafo do meu artigo.
    Olhe a prévia, à direita: o título da seção e o parágrafo aparecem enquanto você digita.
  4. Ligue código e prévia. Clique na palavra “parágrafo” na prévia. O cursor vai para a linha correspondente no código. Agora clique numa linha do código: a prévia mostra o trecho dela.
  5. Acrescente uma lista. Abaixo do parágrafo, digite: 
    = Método
- Coletar os dados.
- Analisar os resultados.
    A estrutura, à esquerda, passa a mostrar Introdução e Método.
  6. Salve. Pressione ⌘S. O Prelo grava seu trabalho e um commit no git.
    O que Salvar faz num projeto sem repositório remoto: a definir.
  7. Exporte o PDF. Clique em Exportar PDF e escolha PDF final.
    Onde o arquivo é gravado e se o app pergunta o local: a definir.

Pronto. Você escreveu um artigo em Typst, viu a prévia acompanhar a digitação, salvou no git e tem um PDF. Para trazer um coautor, siga Como convidar um coautor.

Guias práticos Como fazer

Cada guia resolve uma tarefa. Ele supõe que você já tem um projeto aberto.

Como convidar um coautor

Requer: papel de dono.

  1. Clique em Compartilhar.
  2. Escolha o papel (coautor, revisor ou leitor), a validade e se a entrada exige sua aprovação.
  3. Copie o código de uso único ou mostre o QR. Envie por canal privado: o código contém a chave do documento.
  4. A pessoa instala o Prelo, cola o código em Entrar com convite ou clica no link prelo://join/….
  5. Quando o pedido de entrada aparecer, confira com ela o código da chave e clique em Aprovar.

A pessoa recebe primeiro o texto, depois as figuras e o histórico (D-12). Se ninguém do projeto estiver online, ela pode esperar um aviso ou baixar pelo GitHub.

Para mudar o papel ou remover alguém depois: Compartilhar → participante → Mudar papel ou Remover.

Como revisar sugestões

Requer: papel de dono ou coautor e arquivos sincronizados. Offline, aceitar e rejeitar ficam bloqueados.

  1. Abra o painel de revisão. A estrutura mostra quantas pendências há em cada seção.
  2. Para uma sugestão: clique em Aceitar (⌘↵) ou Rejeitar (⌘⌫) no cartão ou no trecho marcado. ⌥↓ vai para a próxima.
  3. Para várias: filtre por pessoa e por seção, confira a contagem e confirme.
  4. Se errou, clique em Desfazer no aviso ou pressione ⌘Z.
  5. Aceite o commit proposto, ou edite a mensagem.

Uma sugestão com aviso de compilação tem o Aceitar desativado. Rejeite-a ou peça ao autor que a corrija.

Para comentários: responda e clique em Resolver. Para reabrir ou excluir, use a aba Resolvidos. Para excluir uma conversa aberta, use o menu ⋯ do cartão.

Como adicionar bibliografia e imagens

Requer: os arquivos dentro da pasta do projeto. O Prelo não lê nada fora dela.

  1. Copie o .bib (ou .yml no formato Hayagriva) para a pasta do projeto. Se o .typ apontar para um arquivo de fora, o app oferece copiá-lo para dentro (D-13).
  2. Copie as imagens para uma pasta do projeto, por exemplo figures/.
  3. No .typ, aponte para os arquivos: 
    #figure(
  image("figures/fluxo.png", width: 80%),
  caption: [Fluxo de revisão.],
)

Como mostra @silva2024, ...

#bibliography("refs.bib")
  4. Para um estilo de citação próprio, copie o .csl para o projeto e use #bibliography("refs.bib", style: "meu-estilo.csl").
  5. Salve (⌘S) para os coautores receberem os arquivos.

Se o .bib tiver erro, o diagnóstico mostra arquivo e linha. Como adicionar arquivos pela interface (arrastar, menu) e quem pode adicionar, trocar ou remover arquivos: a definir. Limite de tamanho por arquivo: a definir.

Como exportar o PDF

  1. Para enviar à revista: Exportar PDF → PDF final. Sai só o texto aceito, sem marcações nem comentários. Você também pode exportar o .typ limpo.
  2. Para o orientador: PDF com comentários, com os comentários na margem.
  3. Para a resubmissão: PDF de diferenças. Escolha duas versões nomeadas, como “Submissão 1” e “Revisão R1”.
  4. Antes de submeter, abra Preparar submissão: ela lista sugestões pendentes e comentários abertos, e exclui todos os resolvidos de uma vez (só o dono).

Se alguma figura ainda não chegou, o PDF final fica bloqueado e o app lista o que falta. Espere o arquivo chegar.

Se o PDF com comentários e o PDF de diferenças podem sair com figura pendente: a definir.

Como marcar e comparar versões

  1. Abra o Histórico.
  2. Clique em Nomear versão atual e dê um nome, como “Submissão 1”.
  3. Para ver o que mudou entre duas versões nomeadas, escolha as duas e gere o PDF de diferenças.

Para desfazer um aceite ou uma rejeição recente, use ⌘Z.

Voltar a uma versão anterior (restaurar o texto de uma versão nomeada ou de um commit) não está definido nos requisitos: a definir. Até lá, o histórico fica no git do projeto.

Como trabalhar offline

  1. Sem conexão, comente, responda, resolva e sugira normalmente. Cada ação entra numa fila guardada no disco.
  2. Pressione ⌘S: o trabalho fica no computador e a sincronização é agendada.
  3. Ao reconectar, o app recebe, envia a fila, grava no git e libera a edição, nessa ordem.
  4. Se um trecho que você comentou mudou nesse meio tempo, escolha manter o item no trecho novo ou excluí-lo.

Explicação Por quê

Como a colaboração funciona sem servidor

Num editor em tempo real comum, um servidor central recebe as edições de todos, decide a ordem e guarda o documento. O Prelo dispensa esse papel com um CRDT (Yjs): uma estrutura de dados em que as edições de cada pessoa se fundem sem conflito dentro de cada computador, em qualquer ordem, também depois de um período offline. Se a fusão acontece em cada máquina, o servidor não tem mais o que decidir.

Sobra um problema: os computadores precisam se encontrar. Na mesma rede, eles se descobrem pela rede local (mDNS). Pela internet, o iroh abre uma conexão direta e atravessa roteadores e NAT. Quando a rede é fechada demais, o tráfego passa por um relay, sem que o relay consiga ler o conteúdo, porque tudo vai criptografado de ponta a ponta (D-04). O relay pode ser público ou do próprio grupo; essa escolha está a definir.

E quando ninguém está online ao mesmo tempo? Aí entra o git. Salvar e fechar gravam um commit no remoto do grupo (GitHub, GitLab ou outro), e quem abre depois recebe por ali (D-05). Um grupo que queira entrega sem depender de ninguém online pode deixar um computador do laboratório com o Prelo aberto: ele é só mais um participante.

A identidade segue a mesma lógica. Não há conta num serviço; cada pessoa tem uma chave criptográfica criada no próprio computador. O convite carrega a chave do documento, e o dono confere o código da chave de quem entra. O custo dessa escolha é real: sem servidor, “sincronizado” só cobre quem está online e o que já está no git, e redes que bloqueiam UDP dependem do relay.

Por que local-first

Artigos inéditos são material sensível. Se o texto não fica em servidor de terceiros, não há onde ele vazar, e o grupo não precisa contratar nem manter infraestrutura. Por isso nenhum servidor guarda o conteúdo do artigo (RNF-02).

Trabalhar no próprio computador traz uma pergunta: o que fazer offline? A resposta do Prelo é conservadora. Offline você comenta e sugere, porque isso passa por revisão antes de mudar o texto. Editar direto e aceitar sugestões esperam a sincronização, para ninguém escrever sobre uma versão antiga e apagar sem querer o trabalho de outra pessoa. O preço é que quem revisa offline acumula pendências até reconectar (D-06, D-07, D-09).

Salvar faz tudo de uma vez (receber, enviar e gravar no git) porque gestos separados deixam espaço para esquecer um deles (D-08). A consequência é um histórico com muitos commits Prelo sync, e as versões nomeadas existem para marcar os que importam.

Por que Typst

O Typst compila em milissegundos e tem sintaxe mais limpa que a do LaTeX. Compilação rápida é o que permite uma prévia que acompanha a digitação e o teste de cada sugestão em segundo plano: o app compila “texto aceito + esta sugestão” para saber se ela quebra o artigo.

O compilador vem embutido no Prelo, e a versão fica registrada no projeto. Assim ninguém instala nada à parte, e todos os coautores veem a mesma prévia e o mesmo PDF (D-10). A contrapartida: atualizar o Typst exige uma nova versão do Prelo, e uma versão nova pode mudar o layout. Quem decide trocar a versão de um projeto está a definir.

LaTeX fica fora da primeira versão. Quem precisa de controle de alterações em LaTeX já tem o Overleaf; o espaço vazio, segundo o levantamento de novembro de 2026, é Typst com revisão, offline e git juntos.

Por que sugestões não ficam dentro do .typ

Se as marcas de revisão fossem escritas no próprio .typ, quem abrisse o repositório sem o Prelo veria um arquivo sujo, que talvez nem compilasse. Por isso a sugestão é um atributo sobre um trecho do texto compartilhado, guardado em .prelo/ (D-02). O git recebe sempre o texto aceito: sem as inserções pendentes, com o texto das exclusões pendentes. Quem usa VS Code ou o typst de linha de comando continua vendo um projeto Typst normal.

O lado difícil: uma edição feita fora do Prelo chega como diff do git e precisa virar sugestão de um autor “externo”. Como tratar trechos que mudaram dos dois lados ainda está a definir.

Contribuir · como o projeto trabalha

Como contribuir

O Prelo é feito em público, no GitHub. Toda mudança entra pelo mesmo caminho: uma issue, testes escritos antes do código, a suíte inteira verde no seu computador e um pull request que passa no CI em macOS, Windows e Linux. As regras valem para todos, inclusive para o dono do repositório e para os agentes de IA que ajudam no projeto.

Formas de ajudar

Nem toda contribuição é código. Escolha a que combina com você.

Relatar um problema

Abra uma issue dizendo o que fez, o que esperava e o que aconteceu, com sistema e versão. Não precisa saber programar.

Testar em outro sistema

Rode o app no Windows ou no Linux e conte o que quebrou. Cada sistema tem particularidades que o CI nem sempre pega.

Melhorar a documentação

Requisitos, arquitetura e decisões ficam em docs/. Texto confuso, exemplo faltando ou item marcado “a definir” são bons pontos de partida.

Escrever código

Pegue uma issue aberta da fase atual e siga o passo a passo abaixo. Comece pelas menores.

1. Prepare o ambiente

Você precisa de três coisas instaladas antes de clonar o projeto.

Ferramentas necessárias
FerramentaVersãoComo instalar
Rusta de rust-toolchain.tomlrustup instala sozinho ao entrar na pasta

Além disso, cada sistema pede seu próprio pacote:

  • macOS: xcode-select --install.
  • Windows: Microsoft C++ Build Tools e WebView2 (já vem no Windows 11).
  • Linux (Debian/Ubuntu): WebKitGTK 4.1 e afins; a lista completa do apt install está no README.

Depois, clone e instale:

cd prelo
npm install      # instala dependências e liga a trava de push
npm run dev      # abre o app

Deu certo se abrir uma janela “Prelo” mostrando a versão e o seu sistema, por exemplo Prelo 0.1.0 · macos.

2. Escolha ou abra uma issue

Todo trabalho começa numa issue. Assim ninguém faz a mesma coisa duas vezes e cada mudança fica ligada ao motivo dela.

  • Veja as issues abertas. Os rótulos P0 a P3 indicam prioridade; o marco (milestone) indica a fase do plano.
  • Comente na issue que vai trabalhar nela antes de começar.
  • Ideia nova? Abra uma issue citando o requisito que ela atende (RF-xx ou RNF-xx em docs/requisitos.md). Se o requisito não existe, a primeira contribuição é propor o texto dele.
  • O projeto segue uma ordem de fases: editor local, comentários e git, tempo real, modo sugestão, papéis e convites. Trabalho de uma fase futura só entra com justificativa.

3. Escreva o teste antes do código

O Prelo usa TDD (desenvolvimento guiado por testes). Não é preferência: é regra da constituição do projeto, e o motivo é simples. O app guarda textos inéditos e liga computadores diretamente; uma falha de segurança ou uma regressão custa caro.

  1. Vermelho. Escreva um teste que descreve o comportamento esperado. Rode e veja falhar. Se passou de primeira, o teste não está testando o que você pensa.
  2. Verde. Escreva o mínimo de código para o teste passar.
  3. Refatore. Melhore o código mantendo todos os testes verdes.

Três regras complementam o ciclo:

  • Bug corrigido vem com teste que reproduz o bug e falhava antes da correção.
  • Teste de segurança junto com o funcional. Se a mudança recebe dado de fora (arquivo, rede, outro participante), teste também a entrada malformada e a ação proibida.
  • Teste pulado precisa de justificativa escrita num comentário // justificativa: ao lado. Sem ela, a verificação falha.

4. Verifique tudo antes do push

Um único comando roda a suíte inteira: formatação, lint, tipos, testes de todas as camadas e auditoria de licenças e vulnerabilidades.

npm run verify

Ele termina com código 0 só se tudo passar. Quando algo falha, a saída nomeia a etapa e o teste.

Você não precisa lembrar de rodar: o npm install liga um hook de pre-push que roda o verify sozinho e bloqueia o push se algo falhar. Em branches feature/* e na dev, ele roda o modo rápido (verify --quick, sem os testes ponta a ponta); push para a main ou de tag roda a suíte completa. Não use git push --no-verify para contornar; a regra vale para todos, e o CI vai reprovar a mesma coisa depois.

Vai adicionar uma dependência? Ela precisa ter licença permissiva (MIT, Apache-2.0 ou compatível), listada em security/licenses-allow.txt. Vulnerabilidade conhecida de severidade alta ou crítica só entra com exceção em security/vuln-exceptions.toml, com motivo e data de revisão. Na dúvida, pergunte na issue antes.

5. Abra o pull request

O projeto usa gitflow: cada mudança nasce numa branch feature/, entra na dev por pull request, e a dev vai para a main quando sai uma versão. A dev e a main são protegidas: ninguém faz push direto nelas, nem o dono.

Branches e verificações
BranchEntra porHook de pre-pushCI exigido
feature/NNN-nomesai da devmodo rápidoroda no pull request
devpull request de featuremodo rápidoverify no macOS
mainpull request da dev, nas versõessuíte completaverify em macOS, Windows e Linux
  1. Crie a branch a partir da dev atualizada, com o número da issue no nome: git switch dev && git pull && git switch -c feature/042-corrige-titulo.
  2. Faça commits pequenos, com mensagem que diga o que muda e por quê. Deixe o commit do teste antes do commit do código; o histórico mostra o TDD.
  3. Envie a branch (git push; o hook roda o modo rápido) e abra o pull request para a dev.
  4. Na descrição, cite a issue (Fecha #42), os requisitos atendidos e como você testou.
  5. Espere o CI. O merge na dev só libera com o verify verde. A ida da dev para a main, nas versões, exige o verify nos três sistemas.

O pull request está pronto quando: cita a issue, tem testes novos que falhavam antes, passa no CI e não traz dependência fora da lista de licenças.

Ao contribuir, você licencia sua contribuição sob a mesma licença do projeto (MIT OR Apache-2.0), sem CLA.
